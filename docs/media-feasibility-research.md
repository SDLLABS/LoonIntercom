# WP3 media feasibility research

Status: research snapshot, 2026-10-01. No media stack, board, NVR, signaling service, or performance target is selected by this document. No firmware or prototype was built. This report follows [architecture v2](architecture-v2.md), [ADR-0001](adr/0001-no-linux-or-sd-dependency.md), [ADR-0003](adr/0003-independent-bell-failure-domain.md), and [ADR-0004](adr/0004-selective-openchime-port-policy.md).

## Transport roles to evaluate

| Option | Plausible role | Evidence and constraints | Gate before commitment |
| --- | --- | --- | --- |
| P4 RTSP server, NVR pulls | Local NVR ingest; potentially one live diagnostic viewer | Espressif's [RTSP demo](https://docs.espressif.com/projects/esp-adf/en/latest/solution-center/esp-webrtc-solution.html) and [media protocol component](https://components.espressif.com/components/espressif/esp_media_protocols/versions/0.5.0/readme) document server/client and UDP/TCP. The [RTSP service](https://components.espressif.com/components/espressif/esp_rtsp_service/versions/0.5.1/readme) explicitly serves **one** remote client in server role; that limit cannot be assumed adequate for NVR plus viewers. | Confirm NVR H.264 profile, RTP packetization, audio codec, session timeout, transport, auth, and reconnect; test one and multiple clients or use an indoor restreamer. |
| P4 RTSP push, NVR/server accepts | Local NVR ingest when the selected server supports publishing | The same [RTSP service](https://components.espressif.com/components/espressif/esp_rtsp_service/versions/0.5.1/readme) documents a pusher role. NVRs differ in whether they accept RTSP push. | Verify actual NVR ingest contract and outage/reconnect behavior. |
| P4 WebRTC peer to local browser/phone or local media server | Interactive view and talk with secure RTP and adaptive transport | Espressif's [WebRTC solution](https://github.com/espressif/esp-webrtc-solution) provides P4 demos, a local signaling example, H.264 and Opus paths. [RFC 8834](https://www.rfc-editor.org/rfc/rfc8834.html) requires WebRTC RTP congestion adaptation and SRTP. A local signaling/ICE design is still necessary; an external cloud service is not acceptable for core operation. | Prove browser codec/SDP/ICE interop, fully local signaling, authentication, simultaneous audio, reconnect and sustained heap. Determine whether a local gateway is needed for NVR. |
| Local restreamer or media gateway | Fan out one P4 uplink to NVR and multiple viewers, or bridge RTSP to WebRTC | Architectural option only; it adds a local dependency and a new outage case. | Compare its extra latency, power, operations and failure behavior against direct endpoints. Bell and indoor access remain independent. |

RTSP is a media session control protocol [RFC 7826](https://www.rfc-editor.org/rfc/rfc7826.html); it does not by itself provide browser-compatible interactive talk. WebRTC media uses secured RTP and congestion feedback [RFC 8834](https://www.rfc-editor.org/rfc/rfc8834.html). The NVR and interactive viewer may therefore need different transports, but dual transport is not yet a requirement. Check whether one encoded H.264 producer can safely feed both without a second capture/encode path, and whether a slow receiver is dropped without blocking capture. Espressif's [streaming guide](https://docs.espressif.com/projects/esp-vision/en/latest/esp32p4/concepts/codec-streaming.html) describes whole-frame drops for its RTSP example; product behavior must be measured.

## Audio and acoustic path

The candidate data flow is mic PCM → optional AEC/noise processing → Opus or NVR-compatible encoder → transport, plus authenticated remote audio → jitter/decode → speaker PCM. AEC needs the actual speaker playback reference, not merely incoming network packets; [ESP-SR documents a playback reference channel](https://docs.espressif.com/projects/esp-sr/en/latest/esp32p4/audio_front_end/README.html). If playback routing, buffering or clocking misaligns the reference, source availability alone does not prove echo suppression.

[ESP Audio Codec](https://components.espressif.com/components/espressif/esp_audio_codec/versions/2.5.0/readme) lists Opus encode/decode on P4, including 8/12/16/24/48 kHz and configurable 2.5–120 ms frames. Its published **ESP32-S3R8** test at 48 kHz stereo, 90 kb/s, complexity 0 uses 29.4 KB heap and 24.9% CPU for encode, and 26.6 KB heap and 5.86% CPU for decode; stack is excluded. These are source figures, **not P4 measurements**, and cannot be added directly to P4 CPU estimates.

[ESP-SR's P4 AEC benchmark](https://docs.espressif.com/projects/esp-sr/en/latest/esp32p4/acoustic_echo_cancellation/README.html) at 400 MHz reports FD_LOW_COST: 18.9 KB internal RAM, 102.1 KB PSRAM, 3.69 ms per 32 ms frame (11.5% of one core); VOIP_LOW_COST: 26.9 KB internal, 64.1 KB PSRAM, 2.34 ms per 16 ms frame (14.6% of one core). Its [full AFE benchmark](https://docs.espressif.com/projects/esp-sr/en/latest/esp32p4/benchmark/README.html) includes other processing and reaches much larger allocations: one-mic voice-communication low-cost mode is 48.7 KB internal and 819.7 KB PSRAM, with 30.6% feed plus 4.7% fetch on one core. These are alternative configurations, not additive AEC costs. The enclosure's speaker, mic placement, weather seals and gain determine whether any mode is sufficient. Opus remains an option for interactive talk; check selected NVR audio support separately (the current RTSP service lists AAC/G.711, not Opus).

## Preliminary resource worksheet, not a capacity claim

| Item | Calculation or source | Implication to measure |
| --- | --- | --- |
| Raw video frame, YUV420 | `width × height × 1.5`: 1920×1080 ≈ 3.11 MB; 1280×720 ≈ 1.38 MB | Three 1080p frames alone ≈ 9.33 MB before ISP, encoded output, DMA, queues, networking and audio. Check real buffer count and memory caps. |
| Internal versus external RAM | [ESP-IDF P4 external RAM guide](https://docs.espressif.com/projects/esp-idf/en/latest/esp32p4/api-guides/external-ram.html): only a few hundred KB internal RAM; external PSRAM has configuration and compatibility constraints | Record minimum **internal** free heap, largest free block and PSRAM separately at boot, during sessions, and after repeated reconnects. DMA-capable allocations may be more constrained than total PSRAM. |
| Video bitrate and Ethernet | Example planning cases of 2/4/6 Mb/s encoded H.264 equal 0.25/0.5/0.75 MB/s per output, before RTP/TCP/RTCP/SRTP overhead; two 4 Mb/s outputs are about 8 Mb/s application payload | Illustrative numbers, not measured settings. Measure peaks at IDR, packet overhead, retransmission, client fan-out and switch load; reserve bell packet priority on the shared CAT6/PoE topology. |
| PCM audio | 16 kHz × 16 bit × mono = 256 kb/s (32 KB/s) each direction before compression; 48 kHz mono = 768 kb/s (96 KB/s) | Track DMA/ring/jitter buffers and clock drift. A 100 ms 48 kHz mono PCM queue is 9.6 KB per direction. |
| AEC / Opus CPU | P4 AEC figures above; S3 Opus figures above | Measure both together with ISP/H.264, Ethernet, UI, TLS/DTLS, idle and worst-case thermal load; do not extrapolate one benchmark into a whole-system CPU budget. |
| End-to-end latency | Capture exposure/frame period + ISP/encode + send queue + network + receiver jitter/decode/render; audio adds AEC frame, codec packet, jitter and playback | At 30 fps one frame is 33.3 ms; AEC FD benchmark processes 32 ms frames. Neither bounds total latency. Timestamp each stage and record median/p95/p99 under normal and congested LAN. |

At 1080p30, encoded throughput and compute headroom are silicon capabilities, while actual PSRAM bandwidth, DMA placement, shared Ethernet contention and heat are board/system questions. A run must include NVR ingest **and** a talk session concurrently before claiming product feasibility. A clean demo build or a single short video session is insufficient.

## Integration and failure boundaries

- The supervised button and direct RoomKey packet path remain entirely on the bell MCU. P4 media start, stop, errors and watchdogs cannot acknowledge, delay or suppress a press. Shared PoE, switch and cable loss can still stop remote ring delivery; WP2 owns the wired two-device topology and power priority.
- Media uses bounded queues and timeouts. On camera or encoder failure, report video unavailable and restart that pipeline; mic/talk and access requests may continue if resources permit. Audio failure must not disable the bell or indoor access verifier.
- A slow/disconnected NVR or viewer must not accumulate unlimited frames or block capture. Define maximum queue age/bytes, frame-drop/keyframe recovery policy, session count and reconnect backoff before implementation.
- Signaling, RTSP and WebRTC endpoints are network-facing. Require local authentication and bounded parsing/session resources; do not expose media control as an unlock command. RTSP confidentiality/authentication and credential storage need separate decisions for the selected local network; WebRTC SRTP does not authenticate the product's signaling or authorize a viewer by itself.
- Protect audio privacy: only authorized sessions may hear the microphone or send speaker audio. Define clear active-session indication and teardown on auth expiry or disconnect. No cloud or SD dependency may be introduced through a reference demo.
- Measure resource leakage over repeated connection, failed handshake, NVR outage and P4 media task restart. Third-party components need version pinning, license review and a reviewable provenance record before adoption.

## Decision gates and division of work

1. **WP2 hardware gate:** publish exact board revision, camera sensor/driver and capture format, sustained H.264 encode observation, PSRAM/NOR map, wired Ethernet/PoE topology, audio I/O/playback loopback, clocks, thermal and no-SD boot result. A build is not a hardware pass.
2. **Endpoint gate:** identify the actual local NVR and browser/phone clients; record supported H.264 profile/packetization, audio codec, RTSP push/pull and auth, WebRTC H.264/Opus negotiation, local signaling and session count. Do not infer universal NVR support from a protocol name.
3. **Combined-media gate:** on WP2 hardware, collect CPU per core, internal/PSRAM high-water marks, largest free block, bitrate/IDR peaks, dropped frames, audio underruns, AEC quality, latency distribution, and power/thermal data with NVR and talk active together. Set product thresholds before judging results.
4. **Failure gate:** repeat with NVR/broker/signaling down, LAN loss/restore, client churn, malformed/unauthorized requests, camera/audio fault and power recovery; prove the bell direct path remains independent whenever its own power/LAN/RoomKey work.
5. **Decision only after gates:** compare a direct RTSP path, direct WebRTC path and optional local gateway using measured results. Decide whether one or multiple transports, codec mode, session limit, and any prototype should become product work. This report makes no stack commitment.
